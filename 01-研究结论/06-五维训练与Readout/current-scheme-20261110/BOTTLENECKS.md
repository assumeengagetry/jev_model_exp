# 为什么最后几分总提不上去：把事实、解释和未知拆开

[返回总说明](../../../02-研究路径/06-五维训练与Readout/current-scheme-20261110/README.md)。本文不承诺训练某一项就能到28，也不以“模型小”或“再加数据”代替分析。

## 1. 最直接的回答

**我们并不是始终停在同一个地方：Language显著变好了，但其它任务回退，抵消了很多增益；而“其它能力保持、语言专科收益可直接搬进来”这个关键前提没有被实验保证。**

当前最新加速版24.99，离28差3.01。下文详细历史分解保留其原审计口径 **24.97、差3.03**，不把旧预测的错误统计改标签冒称是24.99的新审计。两版差0.02，不改变这条主要现象，但逐任务输出并非完全相同。

## 2. 这3分的账是怎样来的

相对历史受控E31 22.49，当前旧正式版24.97：

| 维度 | E31 Skill | 当前旧正式Skill | Skill差 | 对总分的约贡献 |
|---|---:|---:|---:|---:|
| Knowledge | 8.54 | 9.24 | +0.70 | +0.18 |
| Language | 13.81 | 32.43 | **+18.62** | **+4.81** |
| Retrieval | 37.09 | 36.06 | −1.03 | −0.21 |
| Tools | 43.31 | 31.93 | **−11.38** | **−2.08** |
| Arts | 13.70 | 11.42 | −2.28 | −0.23 |
| 合计 | 22.49 | 24.97 | — | **+2.48** |

Language约+4.81总分被其它四维净−2.33抵消，最后只剩+2.48。不是“补了语言完全没用”，也不是“只差语言再多训一点”。

如果E31其它四维真能完全保持、Language达到旧专科均值35.05，账面约27.98。**这是条件算术，不是训练预测或已存在的模型。**

历史E24最高23.96相同配方重跑20.51，受控mixed为22.49。把单次峰值当稳定起点再叠加另一实验的单维增益，很容易高估“应该到的分数”。

来源：[详细分解](../joint-generic-continuation-20261109/QUALITY-GAP-TO-28-20261110.md)、[机器账目](../../../03-证据与图表/06-五维训练与Readout/joint-generic-continuation-20261109/QUALITY_BREAKDOWN_20261110.json)。旧wrapper与新官方pipeline及加载精度存在差别，**该表是描述性账目，不是同条件因果消融**。

## 3. 不是漏评，回退集中在具体任务

两次正式运行coverage100%，执行和计分请求全部成功。因此“有一批题没有跑进去”不是此次3分缺口的解释。

### 3.1 BFCL：高精确率、低召回的保守调用

同一1,694个case、4,768个真假字段，受控E31与24.97的已有输出逐ID/字段对应：

| 指标 | E31 | 24.97 |
|---|---:|---:|
| 完整case准确率 | 68.77% | **32.94%** |
| 字段准确率 | 88.07% | 75.86% |
| 应调用工具的召回 | 69.60% | **33.00%** |
| 预测调用精确率 | 95.62% | 97.22% |
| TP／FN | 1179／515 | 559／1135 |
| FP／TN | 54／3020 | 16／3058 |
| 整case全判No | 485 | **1120** |
| ROC-AUC | 0.95370 | **0.91042** |

**这是已经观察到的失败形态：需要调用时经常不调用。** 不是“模型乱选工具太多”，也不是靠提高precision解决的问题。

为什么不能先说“调一下bias就行”：

- 1,135个FN中684个P(yes)≤0.1，并非全挤在0.5附近。
- 正字段和负字段log-odds漂移幅度不同，不是同一个常数平移。
- AUC也下降，而正单调概率校准不会修复排序本身。
- 给某字段**所有候选margin统一加同一个截距会在softmax里抵消**；正温度也不改变choice的argmax。

差值截距可能修复一部分召回，但需要独立train-dev证据；不能在BFCL public上扫阈值后当独立成绩。该套件子集每case至少一个正工具，**不能据此硬编码所有外部请求必须选一个**。

### 3.2 PhishNChips：接近随机

raw accuracy从65.15%到50.30%，Skill从30.30到0.60。该任务不在当前允许的训练来源中，不能为了补分把它的公开评测题拿去训练。

相对E31，BFCL约−1.96总分、PhishNChips约−0.90，合计约−2.87；其它任务的正变化已经抵消一部分，**不能把2.87直接加回总分并保证到27.84**。

### 3.3 绝对短板仍在

Knowledge仅约9.2 Skill、Arts约11.4，仍是绝对低位。部分知识推理任务经chance校正后接近0；更多Language曝光不会自动教会这些能力。

Language自身也未全面解决：ACOS、sarcasm、VAST仍弱于HellaSwag/RAGTruth等视图。不能用领域均分隐藏子任务差异。

## 4. 代码已证实的几个“没有对齐”，但还不能全叫回退根因

### 4.1 训练目标与评分单位不同

训练主损失按pair平均BCE；正式BFCL等按完整case是否全对评分。给错一个关键正工具与给错一个普通负候选，对case的影响不同，却可能在pair平均里被很多易负例稀释。

K/R只有3,647条可靠关系辅助，不是全域完整题训练；Tools没有新增可靠case关系。这是结构性差别，**但尚未做受控实验量化改损失的收益**。

### 4.2 工具监督呈现／时间范围不同

训练常见“工具文档是否适用于下一次action”，正式字段则是“目标工具是否应该调用”。selected group还经常不完整；原轨迹没调用某工具也不总等于它不适用。

因此不能从残缺pair拼目录、把所有未出现工具当严格负例，再声称恢复了原生完整gold。该差别长期存在，独自不能解释为什么本轮比旧模型更差。

### 4.3 数量看似平衡，不等于有效信息平衡

- 四域各25万pair，但Knowledge约4,237万token、Arts约1.269亿token，差约3倍。
- ACOS laptop 12,996 pair只有38个review group。
- generic约20% token，却约25% pair，point BCE按pair平均。
- 一个大候选集合或多字段原题可以带来很多训练行，但独立情境没有同比增加。

这些是可从冻结manifest直接核对的事实。是否由它们造成梯度干扰、先验偏移或泛化不足，仍是待验证解释。

### 4.4 训练裁剪与部署完整输入不同

训练最长4096且用head/tail裁剪，正式完整输入最长40960且不截断；Teacher也只看训练组装后的内容。长case中目标工具、约束或证据可能处于被裁掉的中段，**但本轮没有统计具体发生率，不能捏造比例或直接认定全部回退来自此处**。

### 4.5 独立pair读出不是完整选项集推理

当 `criteria_context` 不触发时，一个候选的分数不依赖兄弟候选。候选i/j的 `log(p_i/p_j)=m_i-m_j`，添加第三候选只改归一化，不改两者的相对log-odds。

这是该包装的IIA式限制。某些“选最合适／相对偏好”的任务需要候选间交互，原正则只覆盖部分情况；但不能由这个数学事实推导换head必然提分。readout实验已经表明，完整菜单带来另一种严重顺序风险。

## 5. 为什么最近的readout实验没直接补上这几分

它改变的是另一条研究路线：原标签stage2起点、完整题prompt、题均CE、旧FA3骨干＋FP32投影。**不是在当前24.99权重上只替换一个head。**

本轮最有用的事实：

| 比较 | 观察 | 能说什么／不能说什么 |
|---|---|---|
| frozen新head | 全部质量明显弱于原pair参考 | 500万token有界预算下，仅训头不足；不证明所有head路线永远无效 |
| LoRA适配后 | Cptr五域归一NLL 0.60335，pair0.61497 | 内部质量有信号；不是官方Index增益 |
| 换序 | Cptr79.33%，pair98.67% | 顺序敏感明显，不能当稳健替代 |
| 完整请求速度 | 原始median248.5→94.3ms | 包含pair额外安全准入检查，不能全算模型加速 |
| 扣已测控制开销 | 辅助median104.9→94.3ms | 真实完整请求辅助差约1.11×；非kernel-only |

整题causal菜单里，靠前选项的key看不到后面的选项；code-slot读出也有位置映射问题。**这可解释需要检查的风险，不是本轮已隔离出的唯一原因。** 未执行bidirectional、换序一致性训练、多seed确认或当前joint final上的正式迁移。

## 6. 为什么推理加速也没有涨3分

共享prefix／Graph主要减少重复计算和调度，保留权重及评分公式，本来就不应承诺带来3分能力收益。

实际24.97→24.99只是数值执行变化下的近似相同总分；choice仍有0.8345%改变，不能说逐位无损。它解决的是“9小时能否缩短”，不是“训练目标是否覆盖关键能力”。

新版本丢掉跨field合批，使部分任务反而更慢；这说明工程也需要按完整负载对账，不能拿首500条的加速外推全套。

## 7. 证据等级：现在到底能下什么结论

| 说法 | 等级 |
|---|---|
| 语言增益被其它域回退抵消 | **已有结果支持的描述事实** |
| BFCL主要是漏调用，且排序质量也变差 | **现成逐字段审计支持** |
| 新加速版整套2.765×，非30分钟、非逐位无损 | **完整运行与输出对齐支持** |
| generic阶段造成了全部BFCL回退 | **未知：没有KD-only正式对照** |
| 数据不完整／目标不对齐导致了全部掉分 | **合理研究假设，未受控隔离** |
| 0.6B/rank32容量就是唯一上限 | **未知：没有受控容量曲线** |
| 换Cptr／双向attention一定到28 | **没有证据** |
| 无限加token／调温度就能补3分 | **没有保证** |

## 8. 若以后继续，什么信息最值钱

这不是新增训练授权，也不是本次自动执行计划。它只是说明哪些观察能够减少不确定性：

1. **先保证从当前已训参数接续**，避免再次把“保数据”误当“保能力”。
2. 对Tools用原始train完整case、可靠positive／verified-negative／unknown及与字段读出一致的目标；先解决“到底在教什么”。
3. 预先规定非劣保护，分别看BFCL式召回、Phish类泛化、其它域保持，不只盯平均loss。
4. 若要知道generic边际，必须有受控节点和同条件评估；现有缺失信息无法通过更长文字补出来。
5. Readout先处理换序风险，再谈替换正式Engine；加速分支先恢复合理调度和OOM语义，再谈通用等价。

**总之，过去最不可靠的不是某个超参数小数，而是把几个不同实验的最好结果当成可以无损相加。** 我们现在有了足够结果能定位“损失发生在哪里”，但还没有足够受控证据把它全部归给某一段训练或某一项机制。下一步若继续，应缩小这个不确定性，而不是把“再试一次”当成结论。
