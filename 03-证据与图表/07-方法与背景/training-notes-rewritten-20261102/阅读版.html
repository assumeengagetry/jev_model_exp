第一篇｜模型怎样学会任务

这篇文章串起一次训练中最基本的关系：模型拿什么练习，怎样从练习里学到东西，一次学多少、改多大，以及最后怎样判断有没有学好。第二篇沿着同一条流程，继续解释 GPU 怎样把这些工作做得更省、更快。

从一条样本开始，看模型怎样学到东西

你使用的 Qwen3-0.6B，可以理解为一个已经学过大量知识、现在准备继续练习的模型。名字里的 0.6B 是模型约有 6 亿个参数。参数是模型内部可以调整的数值，模型的知识和做题习惯就体现在这些数值形成的整体结构里。

这次安排的 3M tokens，是累计处理 300 万个文本单位。token 是分词器切出来的片段，可能是一个汉字、半个词或一个标点。它描述练习量；同一段文字读两遍，也会算两遍。于是，0.6B 说的是“参与训练的模型有多大”，3M tokens 说的是“这次让它练多少”。

假设任务是判断两句话是否匹配。模型先读两句话，给出自己的判断；训练程序拿这个判断和正确标签比较，得到一个表示差距的数，这就是 loss，损失。接着，程序沿着刚才的计算过程往回找：内部哪些参数的变化，有助于减小这次差距？这一步得到的信息叫 梯度。最后，优化器根据梯度修改参数，让模型下次有机会答得更好。

整套过程可以记成一条线：做题 → 比答案 → 找调整方向 → 修改参数。技术名称依次是前向传播、计算损失、反向传播、优化器更新。反向传播负责找到调整信息，优化器更新才真正改动模型。理解这两步的区别，后面的 batch 和梯度累积就连起来了。

模型读文本时，注意力负责从上下文里取信息。你配置里的 causal SDPA 就位于这个环节：它按“只能看当前位置及前文”的规则做注意力计算。训练时可以整段并行计算，再用遮挡规则限制谁能看谁。第二篇会继续解释怎样把这部分算得更快。

还有一个容易混淆的地方：读了多少文本，不等于有多少个独立答案。句对分类可以读几百个 tokens，最后只判断一个标签；回答生成也可能读完整个问题，只对回答部分打分。文本量决定了不少计算成本，任务本身决定怎样给模型打分。

一次参考多少条，分几趟处理，每次改多大

你的配置 microbatch 32 × 梯度累积 4，对应有效 batch 128。把它放回刚才的训练过程，就是：显卡先处理 32 条样本，做完前向和反向，把调整信息留下；再处理下一组 32 条。这样重复四趟，汇总 128 条样本的信息，最后才修改一次模型。

这里有两个不同的决定。有效 batch 决定一次参数更新参考多少条样本；microbatch 决定显卡每趟实际处理多少条。 在单卡上，32 条走四趟、16 条走八趟，都能凑成一次参考 128 条的更新。前者和后者的显存、速度可以不同，因为每趟摊开的工作量不同。累积期间，模型参数保持不变；四趟的梯度合在一起，按同一批样本的权重汇总。

这也解释了梯度累积为什么省显存：每趟只需要保留当前 32 条样本的中间计算，做完就能释放大部分“草稿”，留下梯度继续累积。它让一次更新能参考更多样本，而不必把这些样本同时塞进显卡。

接下来才是 学习率：有了调整方向，每次究竟迈多大一步？学习率控制整体调整幅度。你比较的 1e-4 是 5e-5 的两倍，可以直观理解为尝试了更积极的调整。你用的 AdamW 优化器还会参考之前积累的梯度信息，帮助各个参数调整；学习率控制的是这套更新的整体尺度。fused AdamW 则把更新里的多个操作合并执行，减少执行开销，属于参数更新环节的提速。

实验里的 Peak LR 是训练过程中达到的最高学习率。常见安排是先从小学习率慢慢升起来，达到峰值，再逐渐降下去，像先热身、再进入主要练习、最后收稳。

batch 和学习率需要放在一起理解。假设练习材料总量固定，每攒 128 条就调整一次，调整机会会多一些；每攒 256 条才调整一次，每次参考的信息更多，但调整次数会少一些。更大的 batch 并不会自动带来更好的学习效果，因为“每次看得更多”和“总共改得更少”同时发生了。

把实验结果连起来：这轮怎样学得最好

你这轮固定了 3M tokens 的练习预算，训练前 Native 是 0.38。四组设置放在一起，就能看清 batch 和学习率的配合：

一次更新参考的样本数 峰值学习率 Native 得分
128 5e-5 0.35
128 1e-4 0.43
256 5e-5 0.32
256 1e-4 0.34

这轮最好的组合是 batch 128、峰值学习率 1e-4，Native 从训练前的 0.38 到了 0.43。 在 batch 128 时，提高学习率带来了明显改善；换成 batch 256 后，同样提高学习率，改善就小得多。可以把它理解成：在这次有限的练习预算里，较频繁的调整配合更积极的步幅，更适合当前任务。

Native 是你关心的 10 项语言理解任务的平均分，用来观察这次想提升的整体能力。D0 则帮助观察原有任务的保持情况。两者放在一起，才能看到“新东西学得怎样”和“原来的能力还在不在”。

看 D0 时，accuracy 和 loss 又各回答一个问题。accuracy 看最后选没选对，loss 还能反映模型给正确答案多少把握。 举个例子，正确答案是 A：一次给 A 90% 的概率，另一次只给 70%，最后都选 A，准确率没有变化，但第二次的 loss 会更高。也可能有些题始终答错，却变得更加自信，同样会拉高 loss。

因此，你记录里的“D0 accuracy 仍在 80% 左右，loss 略升”，可以直接读成：原任务答对的比例差不多，但模型对答案的概率判断有所变化。这是观察原有能力时需要一起看的两面。

为什么每趟放更多样本，训练反而可能变慢

到这里，学习怎样发生已经清楚了。接下来沿着同一条训练流程，看看 GPU 实际接到了什么工作。

文本长短不一，但普通批处理通常要把一批文本摆成整齐的长方形。假设三条文本分别长 100、200、1000 个 tokens，放在同一批里时，前两条也会补到 1000。补进去的空位叫 padding。这些空位没有真实内容，却仍可能占用显存、经过模型里的部分计算。

这会把 microbatch 和文本长度联系起来。每趟从 32 条加到 64 条，除了样本变多，也更容易遇到一条很长的文本，让其余短文本一起补得更长。你的测试就出现过 padding 比例从约 36% 升到 61% 的情况。显卡忙了更多时间，其中不少工作却花在空位上。

所以，训练速度要看 nonpadding tokens/s，也就是每秒处理多少真实文本。把空位也算进去，会让“做了很多计算”和“处理了很多有效内容”混在一起。另一组固定长度 4096 的测试里，吞吐量一直在约 2.8 万 tokens/s，增大 microbatch 也没明显加速：每趟装更多，已经没有继续换来每秒更多的产出。

减少这类浪费的一种办法，是把长度相近的文本放在一起，这就是长度分桶。第二篇会从这里继续，把分桶、动态填充、FlashAttention、packing 和动态 microbatch 放到各自的位置上。

显存不够时，怎样把同一场训练继续跑下去

可以把显存想成一张工作台。模型参数是长期摆着的工具，梯度和优化器状态是学习记录，中间激活是做题时留下的草稿。模型本身放得下，只说明工具能摆上去；真正训练时，还要给记录和草稿留空间。microbatch 越大、文本越长，同时摊开的草稿通常越多，也就越容易 OOM，也就是显存不足。

前面说的梯度累积，是每趟少摊一些题，分几趟汇总。梯度检查点则是少留一些草稿，需要时重新算一遍。 前向计算时只保留部分中间结果，反向传播需要其他结果时再补算，因此能用额外计算换显存。这两种办法作用在不同地方，可以一起使用。

你的某项测试里，启用检查点后，记录的显存从 8.2 GiB 降到 1.8 GiB，吞吐量下降约四分之一。这个例子很直观：省下了很多草稿空间，但付出了重算的时间。这里的 1.8 GiB 是该项测试的记录，不能直接当成整个 0.6B 模型完整训练的总显存。对长输入来说，关闭检查点会 OOM、开启后能完成，保留它就有实际价值。

这样再看你的配置，每一项都能找到位置：batch 和学习率安排模型怎么学；microbatch、梯度累积和检查点安排 GPU 怎么承受这份工作；Native、D0 accuracy 和 loss 则告诉你，这场训练到底带来了什么变化。

第二篇｜同样的训练，怎样跑得更高效

第一篇讲清了模型怎样学习。这一篇接着看训练流程里的 GPU 执行部分：学习任务已经确定，怎样让显卡少花时间在空位上，让注意力计算更利索，并且让长短不同的样本都能得到合适的处理。

这些技术可以沿着一条线理解：先把样本组得更合适，减少补齐；再把计算做得更高效；进一步把空位从存储和计算里移出去；最后按工作量调整每趟装多少。 它们分别改变不同环节，因此可以组合使用。

先把数据摆好：分桶和动态填充是一套配合

沿用第一篇的例子，三条文本分别有 100、200、1000 个 tokens。普通批处理把每条文本放在独立的一行，并要求这些行一样长。于是三行都占 1000 个位置：第三行正好装满，前两行的大部分位置只能填空。这些空位就是 padding。

长度分桶决定“谁和谁放在同一批”，动态填充决定“这一批每行补到多长”。 分桶会尽量让短文本和短文本一起、长文本和长文本一起；动态填充则看当前批里最长的一条，其他样本只补到这个长度。两者配合，才能把“找到了合适的同伴”真正变成“少补一些空位”。

你的当前做法正是这套组合：先拿出 1024 条样本作为一个局部窗口，在窗口里寻找长度接近的组合，每个 microbatch 放 32 条，再补到当前微批的最长长度，并对齐到 8 的倍数。例如最长 205，就补到 208；最长 2807，就补到 2808。

这个 1024 条窗口可以理解为挑选同伴的范围。范围里有更多候选，就更容易凑出长度相近的 32 条，同时也不用把整个训练集完全排成从短到长。对齐到 8 则是最后再把边缘修整一下，给计算提供更规整的形状。

分桶以后仍有 padding 很正常：同一批的长度只能接近，不会恰好一样；少见的超长样本也不容易找到足够多的同伴。你两次完整训练序列里的 20.6% 和 22.6% padding，说明这套方案已经做过整理，仍留下了大约五分之一的位置空间可以继续研究。

这里也就能分清三件事：分桶让各行原本的长度更接近，动态填充让每批只补到需要的长度，而下一步的 packing／去填充，会进一步改变“每条样本必须占一整行”的存放方式。

再看计算本身：Flash 怎样让注意力更快

数据摆好之后，模型开始计算。Transformer 里一个重要环节是注意力：当前词元应该从哪些词元那里取信息，各取多少。你看到的 Q、K、V，可以简单理解为当前要找什么、其他位置提供什么线索，以及真正取回什么内容。SDPA 是这类注意力运算的名称，Flash 是把它高效算出来的一套方法，cuDNN 则提供了你当前使用的底层实现。

用一个直观画面理解普通注意力：先做一张很大的“词元之间关系表”，再把这张表加工成权重，最后据此汇总信息。序列越长，关系表越大。除了计算本身，把大型中间结果写进显存、再读回来，也会花很多时间和空间。

Flash 的思路是分块处理，边算边汇总，尽量在 GPU 内部较快的小块存储里完成局部工作，避免把完整的大关系表反复搬进搬出。少保存大型中间结果，就能省显存；少搬运这些结果，就能省时间。 它保留了原来的注意力计算含义，所以可以作为执行方式的优化接进训练。

这也解释了它的作用范围：Flash 改善的是注意力怎么执行，长文本需要处理的大量词元关系仍然存在；而且模型还有前馈网络、投影、归一化等其他计算。即使注意力已经很快，padding 仍可能经过其他部分，消耗资源。

你现有的 profile 已经确认，三种代表性输入的前向和反向都走了 cuDNN Flash 类内核。所以，Flash 已经是当前执行路径的一部分。继续做去填充，是顺着数据布局再往前优化；两者能够配合。

把空位挤掉：packing、varlen 和样本边界是一件连贯的事

下面用三条很短的样本说明，长度分别是 3、2、4。普通批处理要把三行都补到 4，总共占 12 个位置；真实内容只有 9 个。去掉空位，再把三条样本紧凑地放在一起，就只需要存这 9 个真实词元。

packing 解决怎样紧凑存放，varlen 让注意力按真实长度和样本边界来计算。 图里的 A、B、C 虽然挨着存放，仍然是三道独立的题。给内核一份边界说明，它就知道哪里是一条样本的开头和结尾。这个例子的边界写成 [0, 3, 5, 9]，意思是从 0 开始，走到 3 结束 A，走到 5 结束 B，走到 9 结束 C。这就是常见的 cu_seqlens，把它理解为一份分段目录即可。

最关键的关系是：存放在一起，计算时仍各算各的。 因果遮挡要求每条样本内部只能看当前位置及之前的内容；padding 遮挡要求空位不能被当作真实内容；样本隔离要求 B 不能因为排在 A 后面，就偷偷读到 A。仅有“只能看前文”的规则，挡不住 B 看前面的 A，因此打包之后必须把样本边界交给计算过程。

插入 EOS、SEP 这类分隔符，像在两道题之间写一条分割线，能表达“这里结束了”，但不会自动建立禁止跨题阅读的屏障。给每条样本重新从 0 编位置编号，也只是恢复各题自己的坐标；真正的隔离仍由边界和注意力执行方式负责。

对你的分类任务，这份边界还要一直保留到输出端。A、B、C 各自要产生一个分类结果，分别对照自己的标签。 如果原来用每条样本最后一个有效词元来分类，打包后就分别找到 A、B、C 的结尾，而不能只取整条打包序列的最后一个位置。样本在内存里连起来了，三个答案仍然要分别交出来。一个句对若共同构成一道分类题，边界就包住整个句对，保留题目内部原本的信息联系。

样本的权重也一样：原来每题一票，打包以后仍每题一票，长题不会因为占的位置多就自动拥有更多话语权。边界、输出和权重都保留下来，改变的才是数据的组织与执行方式。

接下来要看去填充覆盖多远。一种实现只在注意力内部临时去掉空位，算完再放回原来的长方形；其他层仍处理带空位的张量。另一种实现让模型主干全程保持紧凑存储，前馈网络等部分也只处理真实词元。前者省掉注意力里的部分空位工作，后者能覆盖更多层的空位工作。 固定容量的打包块尾部还可能剩一点空位，所以看到 packing 这个名字时，要看它具体采用哪种布局、接通了哪些层。

至于 seqlen_q/k/v、max_seqlen 这些参数，它们就是这份长度说明书的一部分。上例总共存了 9 个词元，最长的一条样本却只有 4 个；总量、最长单条和各段边界，描述的是不同信息。它们要忠实描述数据，不能把数字调小来省算力；能去掉的是没有内容的空位，真实内容要完整保留。

每趟装多少，也应该跟着文本长短变化

前面的分桶、填充和 packing，主要围绕数据怎样摆。另一个维度是每趟给 GPU 多少工作，这就是动态 microbatch要处理的问题。

固定每趟 32 条，只固定了题目数量。32 条每条补到 208，和 32 条每条补到 2808，词元位置数相差 13.5 倍。显卡遇到的工作量很不一样：短文本批次可能还装得下更多，长文本批次却可能撑满显存。

动态 microbatch 的做法就是短文本多装一些，长文本少装一些。可以先给每趟设置一个大致的词元预算，凑到预算附近就处理。仍用长方形布局时，预算要把 padding 占的位置算进去；主干已经全程去填充时，真实词元总数更能反映很多层的工作量。长序列的注意力还会额外增加词元之间的关系计算，所以最终仍要结合实际显存和耗时来选。

这时候，第一篇的有效 batch 又接回来了。你可以继续让一次更新参考 128 条，只改变中间的拆法。举个例子，原来是 32 + 32 + 32 + 32，现在根据长度拆成 64 + 32 + 24 + 8；各趟累积完，仍只更新一次模型。

但大小不同的微批不能简单地每批算一票。64 条所在的一趟，应该汇总 64 条样本的影响；8 条所在的一趟，汇总 8 条的影响。最终每条样本的话语权保持一样，不能因为最后一趟人少，就让其中每条样本被额外放大。 这也是动态调度与学习目标之间的连接：可以灵活搬运题目，原来的评分规则继续保留。

最后，把实际收益落回完整训练。20.6% 或 22.6% 的 padding，告诉你还有多少空位；它不能直接换算成同样比例的加速，因为训练里还有参数更新、数据准备，以及已经由高效内核省掉的部分工作。可以把当前方案作为起点，分别尝试动态 microbatch 和 packing，先确认每条样本的分类结果、损失和梯度保持原来的含义，再比较每秒真实词元数和峰值显存。

profile 在这里像看机器内部的慢镜头，帮助你确认实际跑了哪些内核、时间花在哪。不修改权重，也能执行前向和反向来观察这些过程；但要知道整场训练快了多少，计时就需要覆盖数据准备、前向、反向和参数更新。布局改变以后，再看一次 profile，才能知道新方案实际走上了什么计算路径。

把这些技术放回开头的全景图，就能沿着一条完整的线读下去：分桶挑同伴，动态填充决定行宽，packing 挤掉空位，varlen 保留各题边界，Flash 高效完成注意力，动态 microbatch 决定每趟装多少。 它们共同服务于同一场训练，并通过有效 batch、样本权重和最终评测，与模型怎样学习连在一起。
